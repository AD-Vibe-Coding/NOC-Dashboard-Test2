Prompt to Build the App / Agent Intake Form
Build Objective
Redesign the existing “Start New App / Agent” form so it is not just a tracking form, but a decision-making intake form that helps users determine:

why the App or Agent should be created,
what business problem it solves,
whether it is feasible,
what data/integrations are required,
whether it delivers measurable value,
and whether the expected ROI justifies the effort, token usage, and implementation cost.
The form should guide the user to think through the request clearly before development starts.

Product Requirements Prompt
Design and build a multi-section intake form for creating a new App or AI Agent inside the application.

The new form should replace the current lightweight fields such as:

Type
Status
Name
Category
Customer
Brief overview
Brief benefit
Primary benefit
Progress %
Link
Attachment
Notes
with a more structured intake experience that captures business context, process understanding, feasibility, requirements, and ROI justification.

Core Goal of the Form
The form must help answer these questions before work begins:

What problem are we solving?
Why is an App or AI Agent the right solution?
What is the current end-to-end process?
Which steps are manual vs automated vs AI candidates?
What data, systems, and integrations are required?
What exactly should the system do?
What benefits are expected?
Is there a real ROI or is this only a nice-to-have?
Is the request ready for technical review or build?

Functional Behavior Requirements
The form should include the following behavior:

1. Progressive disclosure
Only show advanced fields when relevant. Examples:

Show integration fields only if “Integrations required = Yes”
Show reviewer fields only if “Human-in-the-loop = Yes”
Show multi-agent design fields only if “Multiple AI Agents = Yes”
2. Smart validation
Prevent submission if critical thinking fields are blank, especially:

Problem statement
Current process
Proposed solution
Data sources
Requirements
ROI inputs
Risks
Readiness
3. Inline guidance
Each section should contain short helper text so users know what good answers look like.

4. Scoring / readiness summary
At the end of the form, generate a summary card showing:

Business clarity
Process clarity
Technical feasibility
ROI readiness
Risk level
Overall readiness
Possible statuses:

Weak business case
Needs more definition
Feasible but requires dev support
Strong candidate for implementation
5. Review summary output
On submission, generate a structured summary for reviewers with these headings:

Business Problem
Current Process
Proposed Solution
Data and Integrations
Requirements
ROI
Risks
Recommendation
Design Requirements
The UI should feel structured, clear, and executive-friendly.

Design guidance
Use a wizard or sectioned form
Include a progress indicator
Group related questions together
Use tooltips/helper text
Use repeatable rows for process steps and requirements
Use auto-calculations for ROI fields where possible
Keep the layout clean and readable
Make required fields obvious
Use warning states if the use case appears weak
Warning logic examples
Show warnings such as:

“No current process time entered — ROI cannot be estimated.”
“No data source identified — technical feasibility is unclear.”
“No business owner selected — request cannot proceed.”
“Benefit is described, but not quantified.”
“This use case may be a nice-to-have rather than a business priority.”

Success Criteria for This Feature
The new intake form should:

improve the quality of app/agent requests,
reduce vague or low-value ideas,
help users determine whether the use case is worth pursuing,
capture enough detail for business and technical review,
highlight ROI and token usage considerations early,
and help teams prioritize high-value, feasible use cases.
